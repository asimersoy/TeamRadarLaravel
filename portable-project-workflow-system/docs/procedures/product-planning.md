# Product Planning

## Trigger

Use this procedure when defining or changing product scope, user journeys,
requirements, architecture, data ownership, execution phases, or completion
criteria.

## Required Inputs

- current state, decisions, open questions, and deferred work;
- known user, business, technical, safety, and operational constraints;
- evidence supporting assumptions that could materially affect scope;
- the approval authority for each unresolved decision.

## Required Records

Create only the records needed for the work:

- project brief for purpose, audience, goals, scope, non-goals, and risks;
- technical specification for architecture, contracts, and constraints;
- execution plan for ordered, verifiable phases;
- completion criteria for the actual definition of done;
- decision and open-question entries for material choices and gates.

Use the matching templates. Link records instead of duplicating their facts.

## Workflow

1. Separate verified facts, owner decisions, assumptions, proposals, and open
   questions.
2. State the objective, user value, explicit non-goals, dependencies, risks,
   and reversibility.
3. Map the intended user journey, including empty, failure, permission, and
   recovery states.
4. Identify data flows, recommendation or ranking effects, external services,
   and review requirements before architecture is locked.
5. Compare viable approaches and record the selected tradeoff.
6. Define acceptance evidence before implementation begins.
7. Order execution so irreversible or expensive work follows validated
   assumptions.
8. Obtain the assigned approvals and update current state.

## Change Control

Implementation may choose ordinary details inside an approved specification.
It must not silently change scope, risk ownership, data behavior, public
claims, or acceptance criteria. Such changes require a visible decision and
updates to every affected record.

## Completion Evidence

Planning is ready for implementation only when scope and non-goals are clear,
blocking questions name an owner, architecture and data contracts agree, risks
have routed reviews, phases have verification gates, and completion criteria
are testable.
